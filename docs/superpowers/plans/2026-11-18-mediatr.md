# MediatR implementation plan

## Design

Route Users and Wallet API use cases through `ISender.Send`. Application command
and query records carry the already-mapped Actor and explicit inputs; public HTTP
DTOs remain unchanged. Existing use cases become `IRequestHandler` implementations
without an extra forwarding service layer. Wallet reads have individual query
handlers; SignalR resolves its authenticated player through a query as well.

Keep authorization, identity resolution and FluentValidation in the handlers in
their existing order. A blanket validation-before-handler behavior would change
403/404 precedence and could validate privileged requests before permission checks.
Domain invariants, transaction boundaries, idempotency, outbox/inbox and notification
delivery remain where they are. MediatR is in-process dispatch; RabbitMQ continues
to carry durable messages between services. Worker loops are unaffected.

Pin MediatR 12.5.0 (Apache-2.0) so the take-home needs no license-key configuration.
Use its built-in DI support, register only each service's Application assembly, and
keep Domain and shared event Contracts independent of MediatR. Application service
registration extensions compose handlers and validators; API hosts call them.

## Review focus

- API Actor must still originate only from verified claims; retain 401/403/404 behavior.
- Transaction validation must follow permission checks and precede receipt reservation.
- Keep the same scoped repositories/unit of work throughout mediator dispatch.
- Preserve cancellation tokens, rollback, retry/concurrency and notification semantics.
- Swagger and Postman must keep the existing HTTP contracts; Docker remains clone-and-run.
